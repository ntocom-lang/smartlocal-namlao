## ขอบเขตที่ทำ

- `/patient-transport`: หน้าเด่น จอง 3 ขั้น ญาติจองแทน ติดตามสถานะ และแจ้งพร้อมรับกลับ ไม่มีเลขสมาชิกกองทุน
- อบต. เป็นผู้ประสานงานตามบัญชีที่ผู้ดูแลกำหนด คนขับมีบัญชีแยก กองทุนไม่ต้องเพิ่มคนใช้ระบบ
- หน้าแรก ServiceHub ชูบริการเมื่อหน่วยงานเปิดใช้แล้ว; ทางเข้าจากหน้าเจ้าหน้าที่และทะเบียนหน่วยงานเจ้าของรถ
- คำขอใหม่แยกจาก `document_requests` และ referral workflow เดิม ประวัติ/เอกสารเดิมคงอยู่ เมื่อเปิด booking mode ลิงก์เดิมเปลี่ยนเข้าจองใหม่ และ trigger กันเบราว์เซอร์เก่าสร้างคิวคู่ขนาน
- ระบบเสนอรวมเที่ยวจากวัน เส้นทาง ความสมัครใจ เวลาและความจุ คนตรวจแผนจาก server ก่อนยืนยัน
- PostgreSQL คำนวณทั้งช่วงรอ/ขากลับและรถวิ่งเปล่า ล็อก settings row ของรถคันเดียวตลอดธุรกรรมเพื่อไม่ให้ยืนยันคิวชนกัน; เที่ยวที่จบก่อนแผนยังกันเวลาตามแผนเดิมแบบ conservative
- ยืนยันเที่ยวตรวจรุ่น settings และทุกรายการจองเทียบแผนที่ตรวจแล้ว ถ้ามีการแก้ pickup แม้เวลาเดิมก็ต้องตรวจใหม่
- คนขับบันทึกรับ/ส่งรายผู้เดินทาง ไม่จบเที่ยวขณะยังส่งคนไม่ครบ ใช้ operation UUID + expected revision กันเน็ตหลุดยิงซ้ำแล้วข้ามขั้น
- มีแจ้งเหตุขัดข้อง ประสานแก้ไข ขอเลิกก่อน/หลังยืนยัน คืนคิวก่อนรถออก และนำรายบุคคลออกหลังประสานแผนดูแลต่อ (ไม่อนุญาตระหว่างอยู่บนรถ)
- เจ้าหน้าที่แก้รายละเอียดคำขอที่ยังไม่ยืนยัน หลังประสานผู้จอง พร้อมเก็บ before/after และเหตุผล ไม่ต้องยกเลิก/กรอกใหม่เพื่อเติมเวลาขากลับ
- ประวัติ audit และแจ้งเตือนในแอปเขียนใน transaction เดียวกัน รายงานเที่ยวปิด 30 วันล่าสุดและงานค้างคำนวณจากข้อมูลจริง ไม่มี LINE/SMS/email/GPS หรือบริการเสียเงินใหม่

## ขอบเขตสิทธิ์

ตารางใหม่เปิด RLS และถอน direct grants จาก PUBLIC/anon/authenticated ตั้งแต่ migration แรก อ่าน/เขียนผ่าน RPC ที่ตรวจ tenant + actor เท่านั้น helper functions ถูก revoke ไม่เปิดให้ client เรียก มี public RPC เพียงข้อมูลบริการ ไม่มีรายชื่อผู้ป่วย

ผู้จองเห็นของตัวเอง รวมที่ยื่นแทน; คนขับเห็นข้อมูลติดต่อและการช่วยเหลือเฉพาะผู้เดินทางที่ยังอยู่ในเที่ยวที่มอบหมาย ไม่มี consent snapshot หรือรายการรอจัดคิว ผู้ประสานงานเห็นทั้งคิวเฉพาะ tenant ของตน ผู้ดูแลตั้งค่าทะเบียนได้ ไม่มีการตัดสิทธิ ลงนาม อนุมัติค่าใช้จ่าย หรืออนุมัติแทนกองทุนอัตโนมัติ

อ้างอิงแนวทางเทคนิค: [Supabase database functions](https://supabase.com/docs/guides/database/functions), [PostgreSQL explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html). การใช้ SECURITY DEFINER ต้องจำกัด search_path และ EXECUTE privileges พร้อมตรวจสิทธิ์เองทุกจุด ไม่มี server key ฝังใน frontend

## เพิ่มปฏิทินและตารางสำหรับประชาชน (อนุมัติในบทสนทนา 2026-09-18)

- ปุ่ม “ดูตารางรถ” และ CTA หน้าแรก สลับ “ปฏิทิน / ตาราง” และจำมุมมองใน localStorage ไม่มีข้อมูลผู้ป่วยอยู่ใน storage นี้
- ดูได้ก่อนเข้าสู่ระบบ กรองเดือน ช่วงวันที่ เส้นทาง และเฉพาะเที่ยวที่ร่วมได้ บนมือถือแสดงตารางเป็นรายการเรียงวัน ไม่ต้องเลื่อนแนวนอน; ตัวกรองละเอียดพับเก็บได้
- Public RPC ส่งเฉพาะช่วงรถถูกใช้ ช่วงว่าง สถานะ และข้อมูลรวมของเที่ยวร่วม ไม่มีชื่อ เบอร์ จุดรับบ้าน รายชื่อสมาชิกเที่ยว หรือข้อมูลการช่วยเหลือรายคน เที่ยวที่ไม่เปิดร่วมซ่อนปลายทางและจำนวนคนด้วย
- จำนวนคนรวมผู้ติดตาม ที่นั่งเหลือคิดจากผู้ที่ยังอยู่ในเที่ยว คำขอรอยืนยันไม่กันที่นั่ง แสดงตามแผนจริงและโหลดใหม่ทุก 60 วินาทีเมื่อหน้าเปิดอยู่/กลับมา focus
- วันหยุด วันงดบริการ วันที่ปฏิทินยังไม่ตรวจครบ และช่วงที่พ้นกำหนดจอง ไม่มีปุ่มขอจองวันว่าง เหตุขัดข้องทำให้วันนั้นไม่แสดงช่วงว่าง
- การขอร่วมเที่ยวเติมวัน เส้นทาง รูปแบบขากลับ และเวลารับกลับ ผู้จองต้องระบุเวลานัดจริงเอง ระบบตรวจความจุ/เวลา/จุดรับในพื้นที่ก่อนรับคำขอ ไม่มีการตีความเวลาออกเป็นเวลานัด
- `requested_trip_id` ผูกคำขอกับเที่ยวเดิม เจ้าหน้าที่ตรวจแผนรวมและประสานเวลาที่เปลี่ยนก่อนยืนยัน `confirm_join` ปรับเที่ยวเดิมภายใต้ resource lock พร้อม revision และ operation UUID ไม่สร้างรถเที่ยวใหม่ซ้อน
- เพิ่มคนได้เฉพาะเที่ยวที่ยังไม่ออก มีผู้เดินทางเดิมที่ยินดีร่วมเที่ยวและเดินได้เองทั้งหมด คนขับต้องตรงค่าปัจจุบัน และไม่มีคำขอยกเลิกค้าง หากเที่ยวเดิมปิด/เปลี่ยนจนร่วมไม่ได้ให้เจ้าหน้าที่ประสานผู้จอง ใช้ยกเลิกและยื่นใหม่เมื่อต้องเปลี่ยนเป็นอีกเที่ยว
- เมื่อยืนยันเพิ่มคน อาจต้องเริ่มรับเร็วขึ้นเพื่อเผื่อจุดรับ ระบบแจ้งในแอปให้ผู้เดินทางเดิม ผู้ขอร่วม และคนขับตรวจแผนล่าสุด ต้องโทรประสานเพิ่มเติมหากเจ้าตัวไม่ได้เปิดแอป
- ช่วงว่างเป็นช่วงตามแผน ไม่รับรองว่าจะพอสำหรับเส้นทางที่เลือก และเวลาเดินทางเป็นค่าที่ตั้งไว้ ไม่ใช่ข้อมูลจราจรสด

ตรวจเพิ่มผ่าน: PostgreSQL ตรวจ public projection, วันหยุด, free intervals ของขากลับภายหลัง, ช่วงวันที่เกินกำหนด, request rollback เมื่อร่วมไม่ได้, การแข่งขันแย่งที่นั่งด้วยแผนเก่า, ยืนยันเข้าเที่ยวเดิมและ retry; Browser ทดสอบผู้ไม่เข้าสู่ระบบ, จำมุมมอง, ขอร่วมจากตารางจนเจ้าหน้าที่รับเข้าเที่ยวเดิมและเต็ม, สองมุมมองที่ 320/390/768/1024px ไม่มี overflow. PGlite ยังเป็น single connection ไม่แทน two-connection race test บน Demo

## ปัญหาที่รู้แล้ว รอแก้ก่อนเปิดใช้จริง: คำขอที่รับจองแทน `created_by` ≠ ผู้จอง (2026-09-22)

คำขอที่เจ้าหน้าที่รับจองแทนทางโทรศัพท์/หน้าเคาน์เตอร์ (`entry_channel = 'staff'`) บันทึก `created_by` เป็นบัญชีเจ้าหน้าที่
แต่หลายจุดยังถือว่า `created_by` = ผู้จอง จึงให้สิทธิ์ของผู้จองกับเจ้าหน้าที่คนที่กรอกเป็นการส่วนตัว
- แก้แล้ว: ฟอร์มหน้าประชาชนเติมค่าจากคำขอของคนที่โทรมา (#264 กรอง `entry_channel !== 'staff'` ก่อนเลือก `lastBooking`)
- ยังค้าง 3 ข้อ (ตรวจจากโค้ด 2026-09-22 ยังไม่มีเทสต์ที่จำลองให้เห็น):
  1. ⚠️ PDPA — เอาเจ้าหน้าที่ออกจาก `coordinator_ids` แล้ว `ptb_role` คืน `citizen` แต่ `patient_booking_mine` ยังคืนคำขอ
     ที่เขาเคยรับแทนครบทุกช่อง (ชื่อ เบอร์ จุดรับ หมุด วันนัด การใช้รถเข็น/เปล) ตลอดที่คำขอเปิด และอีก 30 วันหลังปิด
  2. ยกเลิกได้โดยไม่มีเหตุผลลงประวัติ — `patient_booking_action` ยกเว้นเหตุผลให้ผู้สร้างคำขอ
     (`20260918110200_patient_booking_api.sql` บรรทัด 190) คนที่รับแทนกด "ยกเลิกคำขอ" จากหน้าประชาชนได้
     ขัดกับกติกาที่ว่าการไม่ให้บริการต้องมีเหตุผลเสมอ (ปุ่มยกเลิกในหน้าเจ้าหน้าที่บังคับเหตุผลอยู่แล้ว)
  3. ปุ่ม "พร้อมให้มารับกลับ" มีเฉพาะการ์ดฝั่งประชาชน (`BookingOperations.jsx`) ฐานข้อมูลให้ผู้จัดคิวแจ้งแทนได้ (บรรทัด 195)
     แต่หน้าเจ้าหน้าที่ไม่มีปุ่ม คำขอทางโทรศัพท์จึงแจ้งได้เฉพาะคนที่รับสายตอนจอง ผ่านหน้าประชาชนของตัวเอง
- เจ้าของระบบตัดสิน 2026-09-22: **ยังไม่แก้ ให้แก้ก่อน อปท. จริงเปิดรับจองครั้งแรก** ณ วันนั้นมี `patient_booking_settings`
  เฉพาะ demo และ `patient_booking_submit` ทุกช่องทางบังคับ `enabled` จึงยังไม่มีคำขอจริง แอดมินของ อปท. เปิดเองได้
  ในหน้าตั้งค่า เจ้าของระบบอาจไม่รู้ — ก่อนแตะโมดูลนี้ให้ตรวจ:

```sql
SELECT m.slug, s.enabled FROM public.patient_booking_settings s
JOIN public.municipalities m ON m.id = s.municipality_id;
```

  / `patient_booking_workspace` / `patient_booking_action` + ยกเลิกคำขอ `entry_channel = 'staff'` ต้องมีเหตุผลเสมอ
