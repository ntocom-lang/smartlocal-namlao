## ขอบเขตที่ทำ

- `/patient-transport`: หน้าเด่น จอง 3 ขั้น ญาติจองแทน ติดตามสถานะ และแจ้งพร้อมรับกลับ ไม่มีเลขสมาชิกกองทุน
- อบต. เป็นผู้ประสานงานตามบัญชีที่ผู้ดูแลกำหนด คนขับมีบัญชีแยก กองทุนไม่ต้องเพิ่มคนใช้ระบบ
- หน้าแรก ServiceHub ชูบริการเมื่อหน่วยงานเปิดใช้แล้ว; ทางเข้าจากหน้าเจ้าหน้าที่และทะเบียนหน่วยงานเจ้าของรถ
- คำขอใหม่แยกจาก `document_requests` และ referral workflow เดิม ประวัติ/เอกสารเดิมคงอยู่ เมื่อเปิด booking mode ลิงก์เดิมเปลี่ยนเข้าจองใหม่ และ trigger กันเบราว์เซอร์เก่าสร้างคิวคู่ขนาน
- ระบบเสนอรวมเที่ยวจากวัน เส้นทาง ความสมัครใจ เวลาและความจุ คนตรวจแผนจาก server ก่อนยืนยัน
- PostgreSQL คำนวณทั้งช่วงรอ/ขากลับและรถวิ่งเปล่า ล็อก settings row ของรถคันเดียวตลอดธุรกรรมเพื่อไม่ให้ยืนยันคิวชนกัน; เที่ยวที่จบก่อนแผนยังกันเวลาตามแผนเดิมแบบ conservative
- ยืนยันเที่ยวตรวจรุ่น settings และทุกรายการจองเทียบแผนที่ตรวจแล้ว ถ้ามีการแก้ pickup แม้เวลาเดิมก็ต้องตรวจใหม่
- คนขับบันทึกรับ/ส่งรายผู้เดินทาง ไม่จบเที่ยวขณะยังส่งคนไม่ครบ ใช้ operation UUID + expected revision กันเน็ตหลุดยิงซ้ำแล้วข้ามขั้น
- มีแจ้งเหตุขัดข้อง ประสานแก้ไข ขอเลิกก่อน/หลังยืนยัน คืนคิวก่อนรถออก และนำรายบุคคลออกหลังประสานแผนดูแลต่อ (ไม่อนุญาตระหว่างอยู่บนรถ)
- เจ้าหน้าที่แก้รายละเอียดคำขอที่ยังไม่ยืนยัน หลังประสานผู้จอง พร้อมเก็บ before/after และเหตุผล ไม่ต้องยกเลิก/กรอกใหม่เพื่อเติมเวลาขากลับ
- ประวัติ audit และแจ้งเตือนในแอปเขียนใน transaction เดียวกัน รายงานเที่ยวปิด 30 วันล่าสุดและงานค้างคำนวณจากข้อมูลจริง ไม่มี LINE/SMS/email/GPS หรือบริการเสียเงินใหม่

## ขอบเขตสิทธิ์

ตารางใหม่เปิด RLS และถอน direct grants จาก PUBLIC/anon/authenticated ตั้งแต่ migration แรก อ่าน/เขียนผ่าน RPC ที่ตรวจ tenant + actor เท่านั้น helper functions ถูก revoke ไม่เปิดให้ client เรียก มี public RPC เพียงข้อมูลบริการ ไม่มีรายชื่อผู้ป่วย

ผู้จองเห็นของตัวเอง รวมที่ยื่นแทน; คนขับเห็นข้อมูลติดต่อและการช่วยเหลือเฉพาะผู้เดินทางที่ยังอยู่ในเที่ยวที่มอบหมาย ไม่มี consent snapshot หรือรายการรอจัดคิว ผู้ประสานงานเห็นทั้งคิวเฉพาะ tenant ของตน ผู้ดูแลตั้งค่าทะเบียนได้ ไม่มีการตัดสิทธิ ลงนาม อนุมัติค่าใช้จ่าย หรืออนุมัติแทนกองทุนอัตโนมัติ

อ้างอิงแนวทางเทคนิค: [Supabase database functions](https://supabase.com/docs/guides/database/functions), [PostgreSQL explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html). การใช้ SECURITY DEFINER ต้องจำกัด search_path และ EXECUTE privileges พร้อมตรวจสิทธิ์เองทุกจุด ไม่มี server key ฝังใน frontend

## เพิ่มปฏิทินและตารางสำหรับประชาชน (อนุมัติในบทสนทนา 2026-09-18)

- ปุ่ม “ดูตารางรถ” และ CTA หน้าแรก สลับ “ปฏิทิน / ตาราง” และจำมุมมองใน localStorage ไม่มีข้อมูลผู้ป่วยอยู่ใน storage นี้
- ดูได้ก่อนเข้าสู่ระบบ กรองเดือน ช่วงวันที่ เส้นทาง และเฉพาะเที่ยวที่ร่วมได้ บนมือถือแสดงตารางเป็นรายการเรียงวัน ไม่ต้องเลื่อนแนวนอน; ตัวกรองละเอียดพับเก็บได้
- Public RPC ส่งเฉพาะช่วงรถถูกใช้ ช่วงว่าง สถานะ และข้อมูลรวมของเที่ยวร่วม ไม่มีชื่อ เบอร์ จุดรับบ้าน รายชื่อสมาชิกเที่ยว หรือข้อมูลการช่วยเหลือรายคน เที่ยวที่ไม่เปิดร่วมซ่อนปลายทางและจำนวนคนด้วย
- จำนวนคนรวมผู้ติดตาม ที่นั่งเหลือคิดจากผู้ที่ยังอยู่ในเที่ยว คำขอรอยืนยันไม่กันที่นั่ง แสดงตามแผนจริงและโหลดใหม่ทุก 60 วินาทีเมื่อหน้าเปิดอยู่/กลับมา focus
- วันหยุด วันงดบริการ วันที่ปฏิทินยังไม่ตรวจครบ และช่วงที่พ้นกำหนดจอง ไม่มีปุ่มขอจองวันว่าง เหตุขัดข้องทำให้วันนั้นไม่แสดงช่วงว่าง
- การขอร่วมเที่ยวเติมวัน เส้นทาง รูปแบบขากลับ และเวลารับกลับ ผู้จองต้องระบุเวลานัดจริงเอง ระบบตรวจความจุ/เวลา/จุดรับในพื้นที่ก่อนรับคำขอ ไม่มีการตีความเวลาออกเป็นเวลานัด
- `requested_trip_id` ผูกคำขอกับเที่ยวเดิม เจ้าหน้าที่ตรวจแผนรวมและประสานเวลาที่เปลี่ยนก่อนยืนยัน `confirm_join` ปรับเที่ยวเดิมภายใต้ resource lock พร้อม revision และ operation UUID ไม่สร้างรถเที่ยวใหม่ซ้อน
- เพิ่มคนได้เฉพาะเที่ยวที่ยังไม่ออก มีผู้เดินทางเดิมที่ยินดีร่วมเที่ยวและเดินได้เองทั้งหมด คนขับต้องตรงค่าปัจจุบัน และไม่มีคำขอยกเลิกค้าง หากเที่ยวเดิมปิด/เปลี่ยนจนร่วมไม่ได้ให้เจ้าหน้าที่ประสานผู้จอง ใช้ยกเลิกและยื่นใหม่เมื่อต้องเปลี่ยนเป็นอีกเที่ยว
- เมื่อยืนยันเพิ่มคน อาจต้องเริ่มรับเร็วขึ้นเพื่อเผื่อจุดรับ ระบบแจ้งในแอปให้ผู้เดินทางเดิม ผู้ขอร่วม และคนขับตรวจแผนล่าสุด ต้องโทรประสานเพิ่มเติมหากเจ้าตัวไม่ได้เปิดแอป
- ช่วงว่างเป็นช่วงตามแผน ไม่รับรองว่าจะพอสำหรับเส้นทางที่เลือก และเวลาเดินทางเป็นค่าที่ตั้งไว้ ไม่ใช่ข้อมูลจราจรสด

ตรวจเพิ่มผ่าน: PostgreSQL ตรวจ public projection, วันหยุด, free intervals ของขากลับภายหลัง, ช่วงวันที่เกินกำหนด, request rollback เมื่อร่วมไม่ได้, การแข่งขันแย่งที่นั่งด้วยแผนเก่า, ยืนยันเข้าเที่ยวเดิมและ retry; Browser ทดสอบผู้ไม่เข้าสู่ระบบ, จำมุมมอง, ขอร่วมจากตารางจนเจ้าหน้าที่รับเข้าเที่ยวเดิมและเต็ม, สองมุมมองที่ 320/390/768/1024px ไม่มี overflow. ## คำขอที่รับจองแทน `created_by` ≠ ผู้จอง — แก้แล้ว (2026-09-22)

คำขอที่เจ้าหน้าที่รับจองแทนทางโทรศัพท์/หน้าเคาน์เตอร์ (`entry_channel = 'staff'`) บันทึก `created_by` เป็นบัญชีเจ้าหน้าที่
เดิมหลายจุดถือว่า `created_by` = ผู้จอง จึงให้สิทธิ์ของผู้จองกับเจ้าหน้าที่คนที่กรอกเป็นการส่วนตัว
- #264: ฟอร์มหน้าประชาชนไม่เติมค่าจากคำขอของคนที่โทรมา (กรอง `entry_channel !== 'staff'` ก่อนเลือก `lastBooking` ยังกรองซ้ำไว้)
- `20260922120000_patient_booking_staff_entry_owner.sql` นับ "ผู้จอง" = `created_by = auth.uid() AND entry_channel = 'online'`
  ใน `patient_booking_mine` / `patient_booking_workspace` / `patient_booking_action`
  1. ⚠️ PDPA — ถอดออกจากผู้จัดคิวแล้วไม่เห็นคำขอที่เคยรับแทนอีก (เดิมเห็นครบทุกช่องผ่าน "คำขอของฉัน")
  2. ยกเลิกคำขอที่รับแทนต้องมีเหตุผลเสมอ แม้เป็นคนกรอกเอง (เดิมยกเว้นเหตุผลให้ผู้สร้างคำขอ)
  3. คำขอที่รับแทนไม่ขึ้นใน "คำขอของฉัน" ของคนรับสาย ถือเป็นงานของสำนักงาน จัดการผ่านหน้าเจ้าหน้าที่ตามบทบาท
- ปุ่ม "แจ้งพร้อมให้มารับกลับแทนผู้จอง" ในแผ่นคำขอ (`BookingInbox.jsx`) ใครรับสายก็กดได้ ระบบแจ้งคนขับและบันทึกว่าใครกด
  (เดิมมีแค่ฝั่งประชาชน คำขอทางโทรศัพท์จึงกดได้เฉพาะคนที่รับสายตอนจอง ผ่านหน้าประชาชนของตัวเอง)
- ไม่เปลี่ยน: แจ้งเตือน (`ptb_notice`) ยังส่งถึง `created_by` ข้อความเป็นประโยคทั่วไป ไม่มีข้อมูลส่วนบุคคล ·
  การส่งซ้ำด้วยรหัสคำขอเดิม (`patient_booking_submit` / `_join`) ยังผูกกับผู้กรอก ซึ่งถูกต้องแล้ว

## ผู้จองเห็นเหตุผลที่เจ้าหน้าที่ยกเลิก (2026-09-22)

เดิมหน้าประชาชนขึ้นแค่ป้าย "ยกเลิกแล้ว" คนที่รอรถจึงต้องโทรถามเองว่าทำไมไม่ได้รถ ทั้งที่เหตุผลถูกบังคับให้พิมพ์
และลงประวัติอยู่แล้วทุกครั้ง
- `20260922130000_patient_booking_cancel_reason.sql` ให้ `patient_booking_mine` พ่วงคีย์ `cancel_note`
  มากับคำขอที่สถานะ `cancelled` เท่านั้น อ่านจาก `patient_booking_events` ไม่เพิ่มคอลัมน์และไม่แก้ทางเขียน
  เลือกเหตุการณ์ล่าสุดของคำขอนั้นที่ `action IN ('cancel','cancel_passenger')` และ `actor_id <> auth.uid()`
  (= เจ้าหน้าที่เสมอ เพราะ `mine` ส่งเฉพาะคำขอที่ผู้ใช้จองเองผ่านหน้าประชาชน) · ผู้จองกดยกเลิกเองได้ `null`
  พร้อมดัชนี `patient_booking_events_entity` กันสแกนทั้งตารางทุกครั้งที่ผู้จองเปิดหน้า

  "เหตุผล (ผู้จองจะเห็นข้อความนี้)" เจ้าหน้าที่จะได้รู้ตัวก่อนพิมพ์ · งานภายใน (คืนคิว แก้เหตุขัดข้อง) คงป้ายเดิม

## สถานที่อื่น — ช่อง "อื่นๆ" ในข้อ "โรงพยาบาลที่จะไป" (2026-10-07)

เจ้าของระบบขอให้ผู้จองพิมพ์ชื่อสถานที่ที่ไม่อยู่ในรายการเองได้ และเลือกแบบ **"ค่ามาตรฐานที่แอดมินตั้งครั้งเดียว"** (ไม่แก้ `ptb_plan`)

- **ตั้งค่า:** หน้าตั้งค่าข้อ 4 มีสวิตช์ "เปิดช่อง “อื่นๆ”" + ช่อง "เวลาเดินทางมาตรฐานของสถานที่อื่น (นาทีต่อขา)" (เริ่มต้น = โรงพยาบาลที่ไกลที่สุดที่ตั้งไว้ แก้ได้)
  เก็บเป็นเส้นทางพิเศษ `routes[]` id `'__other__'` มีแค่ `minutes` — ไม่มีคอลัมน์ใหม่ · **ปิดไว้เป็นค่าเริ่มต้น** ไม่มีสวิตช์ = ฟอร์มไม่มีปุ่มอื่นๆ
- **ผู้จอง:** ปุ่ม "อื่นๆ (พิมพ์ชื่อสถานที่เอง)" อยู่ท้ายรายการเสมอ กดแล้วมีช่องพิมพ์ชื่อ (2–200 ตัวอักษร) หน้าทวนก่อนส่งแสดงชื่อที่พิมพ์ ไม่มีช่องขอนั่งร่วม
- **ฐานข้อมูล** (`20261007170000_patient_booking_other_place.sql` แทน 3 ฟังก์ชัน ยกนิยามล่าสุดมาเต็ม + md5 guard):
  `patient_booking_submit` เก็บชื่อที่พิมพ์เป็น `route_label` ของคำขอ (ไหลไปหนังสือ/ใบคำขอ/จอคนขับ/รายงานเหมือนชื่อโรงพยาบาล) และบังคับ `share=false` ·
  `patient_booking_amend` รับ `other_place` (ไม่ส่ง = คงชื่อเดิม ไม่ถูกเขียนทับด้วยป้ายอื่นๆ) · `patient_booking_change_hospital` ปฏิเสธปลายทาง `'__other__'`
- **ทำไมต้อง `share=false`:** `ptb_plan` เทียบปลายทางด้วย `route_id` — ถ้าไม่บังคับ สถานที่อื่นสองแห่งที่ไม่เกี่ยวกันจะถูกมองเป็น "ปลายทางเดียวกัน" แล้วรวมเที่ยวได้
  การรวมเที่ยวต้องให้ทุกใบ `share=true` (`ptb_plan`) จึงไม่เกิด · ปฏิทินสาธารณะเห็น "รถติดภารกิจ ไม่เปิดร่วมเที่ยว" ไม่เห็นชื่อที่พิมพ์ (เทสต์ตรวจแล้ว)
- **เจ้าหน้าที่:** แผ่นรายละเอียดคำขอมีแถว "สถานที่อื่น" เตือนว่าชื่อผู้จองพิมพ์เอง ระบบกันรถตามเวลามาตรฐาน ต้องตรวจระยะทางจริงก่อนยืนยันรถ (ผู้ยืนยันเป็นคนตัดสิน ระบบไม่ตัดสินแทน)
  แก้ชื่อได้ที่ "แก้ข้อมูลหลังโทรประสาน" · เลือก "อื่นๆ" เป็นปลายทางใหม่ในปุ่มเปลี่ยนโรงพยาบาลไม่ได้
- ⚠️ **ข้อจำกัดที่ต้องรู้:** เวลาเดินทางเป็นค่าเดียวของทุกสถานที่อื่น ถ้าสถานที่จริงไกลกว่า รถจะถูกกันสั้นเกินไปจนชนเที่ยวถัดไปได้ — ตั้งค่าให้สูงไว้ก่อน
  ป้องกันด้วยขั้นยืนยันรถที่เป็นคน ไม่ใช่ด้วยระบบ · ผู้พิมพ์อาจใส่ชื่อบุคคลในช่องชื่อ (ฟอร์มเตือนให้ใส่เฉพาะชื่อสถานที่) ข้อความนี้อยู่ใน `route_label` ที่ retention ไม่ลบ
  · รายงานนับตามชื่อที่พิมพ์ (`route_label`) การสะกดต่างกันจึงแยกเป็นคนละแห่ง
- ⚠️ **Compliance:** ระบบไม่ตรวจว่ากองทุนอนุญาตปลายทางประเภทใด (ต้องยืนยันกับข้อบังคับกองทุนฉบับปัจจุบัน) · ผู้จัดคิวตัดสินตอนยืนยันรถเหมือนเดิม
- **ลำดับ release:** apply migration (md5 guard หยุดทั้งก้อนถ้านิยามบนฐานจริงไม่ตรงรีโป) → merge/deploy → ไล่ chunk ยืนยัน → **แล้วค่อยให้แอดมินเปิดสวิตช์** ·
  ถ้าเปิดสวิตช์ก่อน apply: submit รุ่นเก่าไม่รู้จัก `other_place` จะเก็บป้าย "อื่นๆ" เป็นปลายทางและคงค่า share ตามที่ส่ง · แท็บเก่าที่ยังเปิดอยู่หลังเปิดสวิตช์จะเห็นปุ่มอื่นๆ
  แต่ไม่มีช่องพิมพ์ ส่งแล้วฐานข้อมูลปฏิเสธ ("กรุณาพิมพ์ชื่อสถานที่ที่จะไป") ต้องรีโหลดหน้า

  ต้องเลือกโรงพยาบาลในรายการ (แผ่นแก้ข้อมูลแสดงเส้นทางเดิมเป็น "ไม่อยู่ในตั้งค่าแล้ว")

- **รายงาน:** `servicePeriodReport` ดึงแถวรายวันช่วงเดียวกัน · ระยะทาง = ผลรวมของวันที่มีเที่ยวจบแล้วในรายงาน วันละครั้ง · วันที่ไม่มีเลขไมล์/รอตรวจสอบนับ "ยังไม่ครบ" ไม่ใช่ 0 ·
  รายงานกรองบริการ = ระยะของรถทั้งวันที่มีบริการนั้น (วันที่มีทั้งผู้ป่วยและชุมชนแบ่งไม่ได้) · ใบสรุปพิมพ์ 1 แถว = 1 วัน (ปลายทาง/เลขหนังสือ/คนขับของทั้งวันในแถวเดียว)
  · ข้อมูลที่ไม่มี `days` (รุ่นก่อน/ตัวจำลองในเทสต์) ยังใช้ระยะรายเที่ยวเดิม
- ⚠️ **ผลที่ต้องรู้:** ไม่มีระยะทางรายเที่ยว/รายปลายทาง/รายผู้ป่วยอีก — ถ้ากองทุนเบิกจ่ายรายเที่ยวต้องยืนยันกับกองทุน · เลขออกต่อจากเลขล่าสุดเสมอ
  ถ้ารถถูกใช้นอกระบบระหว่างวัน ระยะนั้นไปรวมในวันถัดไป · คนขับลืมใส่ = วันนั้นค้างในรายการ ไม่เดาให้
