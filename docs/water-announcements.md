# ประกาศสถานการณ์น้ำ-ฝนของ อปท. ที่มีผู้ยืนยัน (เฟส 2 · PR 2.1 ส่วนฐานข้อมูล)

## หลักการ (เส้นที่ห้ามข้าม)

การประกาศเตือนภัยเป็นดุลพินิจและอำนาจของผู้บริหารท้องถิ่น — **ระบบร่าง คนกดยืนยัน** ไม่มีคนกด = ไม่มีอะไรออก ระบบไม่ประกาศแทน ไม่สั่งอพยพ ไม่ประเมินความเสียหาย ไม่ตัดสินสิทธิ์ใคร

⚠️ **ผู้มีอำนาจประกาศตามกฎหมายและแผนป้องกันและบรรเทาสาธารณภัยของ อบต. ต้องยืนยันกับตัวบทฉบับปัจจุบันก่อนเปิดกับ อปท. จริง** (ไม่ได้อ้างเลขมาตราหรือชื่อกฎหมายไว้ในโค้ด/เอกสารนี้) — จึงปิดเป็นค่าเริ่มต้น เปิดทีละ อปท. เมื่อ อบต. ยืนยันแล้ว ทดสอบบน demo (สนามซ้อม) เท่านั้น

## PR 2.1 ทำอะไร (ยังไม่มีหน้าจอ ยังไม่ส่งข้อความหาใคร)

| ส่วน | ทำอะไร |
|---|---|
| `water_announcement_tick()` | cron ทุกชั่วโมงนาทีที่ 25 (หลังตัวจดเหตุการณ์นาทีที่ 20) ร่างข้อความจากเหตุการณ์ที่เปิดอยู่ของ อปท. ที่ **เปิดใช้** เท่านั้น |
| `approve_water_announcement(id, ชั่วโมง)` | ผู้มีสิทธิ์กดยืนยัน → ขึ้นหน้าประชาชน · อายุค่าเริ่มต้น 24 ชม. สูงสุด 72 · ครบแล้วหายเอง |
| `decline_water_announcement(id)` | เลือก "ไม่ประกาศ" (บันทึกผู้ตัดสิน · ไม่ร่างซ้ำเรื่องเดิม 12 ชม.) |
| `cancel_water_announcement(id)` | ยกเลิกฉบับที่เผยแพร่ → หายจากหน้าประชาชนทันที |
| `list_water_announcements(อปท., จำนวน)` | หน้าเจ้าหน้าที่อ่าน (ผู้ที่ดูเหตุการณ์น้ำ-ฝนได้) · ส่ง `can_approve` ให้หน้าจอซ่อน/แสดงปุ่ม |
| `get_public_water_announcement(อปท.)` | หน้าประชาชนอ่านเฉพาะฉบับที่ยืนยันแล้วและยังไม่หมดอายุ — ส่งแค่ id · ข้อความ · เวลาเผยแพร่/หมดอายุ · ชื่อ อปท. (ไม่ส่งชื่อผู้ยืนยัน) |

## ใครยืนยันได้

บัญชีที่ตรงกับ **ผู้ลงนามระดับหน่วยงานที่ active วันนี้ในทะเบียนผู้ลงนามกลาง** (เมนู "ผู้ลงนามเอกสาร" ชุดเดียวกับคำร้อง/ใบใช้รถ) บทบาท **นายก + ปลัด** และบัญชีนั้นต้องเป็น admin/officer/staff ของ อปท. เดียวกัน

- ไม่ใช่ superadmin/admin ทั่วไป (ผู้ดูแลระบบไม่ใช่ผู้มีอำนาจประกาศ) · ไม่ใช่หัวหน้ากอง · ไม่ใช่ผู้ลงนามกำหนดเอง
- ผู้ลงนามที่ทะเบียนกรอกชื่อเอง (ไม่มีบัญชี) กดไม่ได้ = **ไม่มีประกาศออก** (ตั้งใจ)
- หมดวาระ/ปิดแถว/ยังไม่ถึงวันเริ่ม = กดไม่ได้ทันที (เทียบวันที่ไทยทุกครั้งที่กด)
- ไม่เพิ่มคอลัมน์สิทธิ์ใน `profiles` (เส้นทางนั้นเคยทำระบบพังมาแล้ว) — ค่าตั้งต้น **นายก + ปลัด เป็นของผู้พัฒนา ไม่ได้อ้างระเบียบใด** ถ้า อบต. ยืนยันว่าผู้มีอำนาจเป็นอย่างอื่น แก้ที่ `water_announcement_approver_roles()` จุดเดียว

## ข้อความร่าง

ค่าที่วัดได้ล่าสุดของสถานีที่ทำให้ระบบเปิดเหตุการณ์ + เวลาวัด (เวลาไทย พ.ศ.) + "ไม่ใช่การพยากรณ์" ตัวอย่าง:

> ประกาศจาก อบต.… / ข้อมูลสถานการณ์น้ำ-ฝน ณ … / ระบบเฝ้าระวังเปิดเหตุการณ์เมื่อ … จากค่าที่วัดได้ใกล้พื้นที่ ค่าล่าสุดมีดังนี้ • สถานีฝน … วัดฝนสะสม 24 ชั่วโมงได้ … มม. (วัดเมื่อ …) • … ค่าข้างต้นเป็นค่าที่สถานีวัดได้ ไม่ใช่การพยากรณ์ ขอให้ติดตามประกาศจาก … ต่อไป

- **ไม่มีข้อความ "ควรทำอะไร"/อพยพ/รับรองความปลอดภัย** จนกว่า อบต. ให้ข้อความตามแผนของตน (เทสต์ห้ามคำเหล่านี้ในตัวสร้างข้อความ)
- ค่าว่างไม่กลายเป็น 0 (ค่า 0 ที่วัดได้จริงยังพูดว่า 0) · ใช้เฉพาะค่าที่วัดภายใน 3 ชม. · ไม่มีค่าสดเลย = ไม่ร่าง
- ร่างเฉพาะตอนสัญญาณยังเข้าเกณฑ์ในรอบตรวจล่าสุด (เหตุการณ์กำลังสงบ/ตัวจดหยุด = ไม่ร่าง)
- ข้อความเตือนของ สสน. บอกเพียงว่ามี + เวลา ให้ดูฉบับเต็มที่หน้าสถานการณ์น้ำ-ฝน (ไม่คัดลอกข้อความหน่วยงานอื่นเข้าประกาศของ อปท.)
- สถานีเกิน 6 แห่ง → "และสถานีอื่นอีก N แห่ง"
- ร่างอายุ 3 ชม. เกินนี้ถูกทิ้งและร่างใหม่ด้วยค่าล่าสุด · กดยืนยันร่างเก่า/ร่างของเหตุการณ์ที่ปิดแล้วไม่ได้

## สถานะของประกาศ

`draft` ร่างรอยืนยัน → `published` เผยแพร่ → `expired` ครบอายุ / `cancelled` ยกเลิก / `superseded` ถูกฉบับใหม่แทน · `declined` เลือกไม่ประกาศ · `lapsed` ร่างที่ไม่ได้ใช้ (เก่าเกินอายุ/เหตุการณ์สิ้นสุดก่อนมีคนยืนยัน — ไม่เคยขึ้นหน้าประชาชน)

- หน้าประชาชนตัดสินจาก `expires_at` เอง **ไม่ต้องรอ cron** (ครบอายุหายทันที) — cron แค่เก็บสถานะให้ตรง
- ฉบับที่เผยแพร่เหลือเวลา < 3 ชม. และเหตุการณ์ยังเข้าเกณฑ์ → ร่างฉบับต่ออายุให้ยืนยันใหม่ (ยืนยัน = ฉบับเดิมถูกแทนในธุรกรรมเดียว) · ต่ออายุโดยแก้เวลาตรงๆ ไม่ได้
- ร่าง/ฉบับเผยแพร่ ซ้อนได้ทีละ 1 ต่อ อปท. (unique index ชนที่ฐานข้อมูล ไม่พึ่งหน้าจอ)

## ตัวล็อกข้อมูลและบันทึกย้อนตรวจ

- ข้อความ/ที่มา/เวลาร่าง/หน่วยงานของประกาศ **แก้ไม่ได้** · ลบแถว/ล้างตารางไม่ได้ (trigger ล็อก แม้เป็นเจ้าของฐานข้อมูล) · ฉบับที่ปิดแล้วฟื้นไม่ได้ · สถานะเปลี่ยนได้ตามเส้นทางที่กำหนดเท่านั้น · ลบ อปท. ทั้งก้อน (FK cascade) ยังทำได้
- ข้อความที่ผู้มีสิทธิ์ยืนยัน = ข้อความที่ระบบร่าง (ตรวจย้อนได้ว่าประกาศอะไร ตามค่าอะไร)
- ทุกการตัดสินของคน (ยืนยัน/ไม่ประกาศ/ยกเลิก) เขียนลง `audit_logs` เดิมฝั่งเซิร์ฟเวอร์ (หน้าจอข้ามไม่ได้) — `approve` / `reject` / `cancel` · `resource_type = water_announcement` · metadata มีแต่ id เหตุการณ์/ชั่วโมง ไม่มีข้อมูลบุคคลอื่น
- ตารางปิดสนิท (RLS เปิด ไม่มี policy ถอนสิทธิ์ anon/authenticated ทั้งหมด) อ่าน/เขียนผ่านฟังก์ชัน SECURITY DEFINER เท่านั้น · ไม่เก็บชื่อ เบอร์ พิกัดของบุคคล

## วิธีเปิด/ปิด (เจ้าของระบบ — ฝั่ง SQL editor)

```sql
-- เปิดบน demo (สนามซ้อม) เพื่อทดสอบ
INSERT INTO public.water_announcement_settings (municipality_id, enabled)
SELECT id, true FROM public.municipalities WHERE slug = 'demo'
ON CONFLICT (municipality_id) DO UPDATE SET enabled = true, updated_at = now();

-- ปิดทันที (หน้าประชาชนหยุดแสดงฉบับที่ค้างอยู่ด้วย)
UPDATE public.water_announcement_settings SET enabled = false, updated_at = now() WHERE municipality_id = '<id>';

-- หยุดร่างทั้งระบบ
SELECT cron.unschedule('water-announce-tick-hourly');
```

⚠️ **ห้ามเปิดกับ อปท. จริงจนกว่า อบต. จะยืนยันผู้มีอำนาจประกาศจากตัวบทและแผนฉบับปัจจุบัน** และมีหน้าจอยืนยันใช้งานได้ (PR 2.2) — ตอนนี้ยังไม่มีหน้าจอ ผู้มีสิทธิ์ยืนยันผ่านหน้าเว็บยังไม่ได้

## ค้าง / ขั้นต่อไป

- **PR 2.2** หน้าเจ้าหน้าที่: ปุ่ม "ยืนยันประกาศ" ปุ่มเดียว (ผู้มีสิทธิ์เท่านั้น) + แถบประกาศฝั่งประชาชน (ชั้นประกาศ อบต. ชนะข้อมูลดิบ) · งานเจ้าหน้าที่ต้องไม่เพิ่ม
- **PR 2.3** ส่งเข้ากลุ่ม Telegram ผู้นำหมู่บ้าน (Edge Function ต้อง deploy เอง) · ข้อความเสียงตามสาย · ภาพแชร์
- ไม่มีแยกรายหมู่ (เฟส 1 ถูกถอดเพราะไม่มีพิกัดหมู่) — ประกาศเป็นระดับตำบล
- ข้อความ "ควรทำอะไร" รายระดับ ต้องมาจากแผนของ อบต. เอง (ยังไม่มี)
- ผู้อนุมัติไม่กดทัน → ร่างค้างแล้วหมดอายุเอง ประชาชนไม่ได้ประกาศ — ระบบไม่ประกาศแทน (ยอมรับ)
