# เหตุการณ์น้ำ-ฝนที่ระบบจดเอง (เฟส 3 · PR 3.1 ส่วนเก็บ + PR 3.2 หน้าเจ้าหน้าที่ + PR 3.3 สรุป A4)

## ทำไมต้องมี

`water_readings` และ `water_warnings` ลบที่ 7 วัน พอเหตุการณ์ผ่านไปหนึ่งสัปดาห์ไม่เหลือบันทึกว่าน้ำขึ้นสูงสุดเท่าไร ขึ้นตอนไหน สสน. เตือนอะไร — ย้อนเก็บทีหลังไม่ได้ ต้องเริ่มเก็บก่อนเกิดเหตุ
PR 3.1 ทำ "ส่วนเก็บ" (ตาราง + ฟังก์ชัน + cron) · PR 3.2 เพิ่ม "หน้าเจ้าหน้าที่" อ่านอย่างเดียว (ด้านล่าง) · ไม่ส่งข้อความหาใคร ไม่มีอะไรออกสู่ประชาชน · PR 3.3 เพิ่มปุ่ม "พิมพ์สรุป A4" ในหน้ารายละเอียด (ด้านล่าง)

## ระบบทำอะไร

`water_event_tick()` รันทุกชั่วโมงนาทีที่ 20 (sync นาทีที่ 10 → แจ้งเตือน Telegram นาทีที่ 15 → ตัวนี้) อ่านจากฐานข้อมูลเราเท่านั้น

**เปิดเหตุการณ์** เมื่อ "ค่าสด" ของ อปท. ที่เปิดโมดูลน้ำ-ฝน เข้าเกณฑ์ข้อใดข้อหนึ่ง — ชุดเดียวกับที่ส่งเข้ากลุ่ม Telegram ยกเว้นอ่าง:

| สัญญาณ | เกณฑ์ | ความสดของค่า |
|---|---|---|
| ฝน | 24 ชม. ≥ 90.1 มม. (ฝนหนักมาก ตามกรมอุตุฯ) | ไม่เกิน 3 ชม. |
| ระดับน้ำ | ต่ำกว่าตลิ่งไม่เกิน 1 ม. (ขั้นเฝ้าระวังขึ้นไป ตามกรมชลฯ) | ไม่เกิน 3 ชม. |
| สถานีเตือนภัย ews | ระดับ 2–3 (ตอนนี้ปิดใช้งานอยู่ทุกแถว) | ไม่เกิน 12 ชม. |
| ข้อความ สสน. | ระบุอำเภอ+จังหวัดเดียวกับ อปท. | ออกไม่เกิน 6 ชม. |

⚠️ **อ่างเก็บน้ำไม่ใช้เปิดเหตุการณ์** — อ่างอยู่ชั้น "น้ำมาก" (>80%) ได้เป็นเดือนในฤดูฝน เหตุการณ์จะไม่ปิด
ค่าว่างจากต้นทางไม่เข้าเกณฑ์และไม่ถูกแปลงเป็น 0 (ระดับน้ำว่างห้ามกลายเป็น "เสมอตลิ่ง")

**ระหว่างเหตุการณ์** คัดลอกค่าที่วัดได้ของทุกสถานีที่ใช้งานอยู่ของ อปท. (ฝน/ระดับน้ำ/อ่าง/ews) ลง `water_event_readings` ทุกรอบ พร้อมย้อนหลังก่อนเปิด 24 ชม. เพื่อเห็นช่วงน้ำกำลังขึ้น และคัดลอกข้อความ สสน. ของอำเภอ+จังหวัดนี้ลง `water_event_warnings` ตามต้นฉบับ

**ปิดเหตุการณ์** (ระบบปิดเอง ไม่มีคนกรอก):

| เหตุผล `close_reason` | เงื่อนไข |
|---|---|
| `calm` | ค่าสดไม่เข้าเกณฑ์ต่อเนื่อง 24 ชม. · รอบที่ไม่มีค่าสดพอตัดสิน (สถานีฝน/ระดับน้ำไม่ส่งค่าจริงภายใน 3 ชม.) **ไม่นับว่าสงบ** และเริ่มนับ 24 ชม. ใหม่ · เข้าเกณฑ์อีกครั้งก็เริ่มนับใหม่ |
| `data_lost` | ไม่มีค่าสดพอตัดสินเลย 48 ชม. (สถานีถูกปิด/ต้นทางล่ม) — ไม่ปล่อยค้างตลอดไป |
| `module_off` | อปท. ปิดโมดูลน้ำ-ฝน หรือถูกปิดใช้งาน |

ทุกเหตุการณ์จดเหตุผลที่ตรวจย้อนได้: `open_reason` = สถานีไหน ค่าเท่าไร วัดเมื่อไร (พร้อม `rule_version`) · `close_reason` + `ended_at` (เวลาที่เห็นสัญญาณ/ค่าสดล่าสุด) + `closed_at` (รอบที่ปิด)
อปท. หนึ่งมีเหตุการณ์เปิดค้างได้ทีละเรื่อง (unique index) · อปท. หนึ่งพังไม่ลากรอบของแห่งอื่นล้ม และลง `job_heartbeats` ชื่อ `water-event-tick`

## ตาราง (ปิดสนิท ไม่มี policy อ่านตรง — อ่านผ่านฟังก์ชันเท่านั้น)

- `water_events` — 1 แถวต่อเหตุการณ์
- `water_event_readings` — สำเนาค่าที่วัดได้ **พร้อมชื่อสถานี ไม่ผูก FK ไป `water_station_config`** เพื่อให้ลบ/เปลี่ยนสถานีทีหลังแล้วบันทึกเก่าไม่หาย
- `water_event_warnings` — ข้อความ สสน. ตามต้นฉบับ

ไม่เก็บชื่อ เบอร์ พิกัดของบุคคล (เทสต์ตรวจชื่อคอลัมน์) · RLS เปิด ถอนสิทธิ์ anon/authenticated ทั้งหมด · `water_event_tick` เรียกจากเว็บไม่ได้

## หน้าเจ้าหน้าที่ "เหตุการณ์น้ำ-ฝน" (PR 3.2)

เมนูใต้ "สำนักปลัด" ข้างตารางเก็บขยะ · **อ่านอย่างเดียว ไม่มีอะไรให้เจ้าหน้าที่กรอก/ยืนยัน/ลบ** (เจ้าของระบบสั่ง 2569-10-17 "ต้องไม่เพิ่มงานให้เจ้าหน้าที่") — เปิดดูตอนมีคนถามเท่านั้น ไม่ขึ้นในรายการ "ต้องทำตอนนี้" เพราะไม่มีอะไรให้ทำ

| ส่วน | ทำอะไร |
|---|---|
| แถบสถานะตัวจด | "ระบบตรวจล่าสุด 17:20 น." (เขียว) · เงียบเกิน 3 ชม. = "ไม่ได้ตรวจมา X ชม. ข้อมูลช่วงนี้อาจไม่ครบ" (เหลือง) · ไม่มีบันทึกเลย = เทา — **บอกสถานะเฉยๆ ไม่สั่งให้ใครทำอะไร** (แยก "ว่างเพราะสงบ" จาก "ว่างเพราะระบบเงียบ") |
| รายการเหตุการณ์ | ใหม่ → เก่า (สูงสุด 50) · ช่วงเวลา · สาเหตุที่ระบบเปิด · ฝนสูงสุด/ใกล้ตลิ่งสุด · เหตุผลที่ระบบปิด |
| ตอนไม่มีเหตุการณ์ | อธิบายเกณฑ์ 4 ข้อ + เหตุที่อ่างไม่ใช่ตัวเปิด + ระบบปิดเอง (ตอบคำถามว่า "ทำไมไม่มีอะไร" ได้ในหน้าเดียว) |
| รายละเอียด | รายสถานี (ค่าสูงสุดพร้อมเวลา · กราฟเส้นเล็ก · ช่วงที่สถานีไม่ส่งค่า) · ข้อความเตือน สสน. ตามต้นฉบับ · คำกำกับว่าไม่ใช่การประเมินความเสียหาย |

**ใครเห็น:** superadmin · admin · officer · staff ของ อปท. ที่เปิดโมดูล "สถานการณ์น้ำ-ฝน" (ไม่เพิ่มคีย์ใน `enabled_modules` — ไม่ต้องแตะข้อมูลทุก อปท.) · ช่าง/สภา/ประชาชนไม่เห็น · บทบาทฝั่งหน้าเว็บ (`hasWaterEventsAccess` ใน StaffDashboard.jsx) ต้องตรงกับ `can_view_water_events()` ฝั่งฐานข้อมูล — เทสต์เทียบให้ · ⚠️ ยังไม่มี อบต. ยืนยันว่ากองไหนดูแลงานป้องกันสาธารณภัย (ไม่ได้อ้างระเบียบใด) เปลี่ยนได้ที่ฟังก์ชันนี้กับ StaffDashboard.jsx

**ฟังก์ชันอ่าน** (`20261017100000_water_events_staff_rpc.sql` ของใหม่ล้วน ไม่ทับของเดิม · SECURITY DEFINER ตรวจบทบาทและ อปท. ในฟังก์ชัน · STABLE ไม่เขียนอะไร):
- `list_water_events(_municipality_id, _limit)` — รายการ + `recorder` (เวลาที่ตัวจดทำงานจบรอบล่าสุดจาก `job_heartbeats` ส่งแค่เวลา ไม่ส่งข้อความ error)
- `get_water_event(_municipality_id, _event_id)` — ค่ารายสถานี + ข้อความ สสน. · เหตุการณ์ของ อปท. อื่นได้ NULL
- ไม่เปิด policy อ่านตารางตรง เพราะเหตุการณ์ 72 ชม. ≈ 1,000 แถว ใกล้เพดาน 1,000 แถวของ Supabase (อ่านตรงจะหายเงียบ) — ฟังก์ชันรวมเป็น jsonb ก้อนเดียว (เทสต์ 1,200 แถว)
- ⚠️ ต้อง apply migration ก่อน merge โค้ด: ฟังก์ชันไม่พร้อม = หน้าขึ้นข้อความ "ระบบฐานข้อมูลยังไม่พร้อมสำหรับหน้านี้" + ปุ่มโหลดใหม่ (ไม่พังทั้งหน้าเจ้าหน้าที่)

**กติกาที่ล็อกด้วยเทสต์:** ไม่มี input/textarea/select/form และปุ่มมีแค่ เปิดรายละเอียด/กลับ/โหลดใหม่ · ไม่มีคำขอเขียน ไม่อ่านตารางตรง · ค่าว่างแสดง "ไม่มีค่า" ไม่ใช่ 0 · เส้นกราฟขาดตรงช่วงสถานีไม่ส่งค่า (ไม่ลากข้าม) · ข้อความ สสน. แสดงตามต้นฉบับ (ไม่ตีความ HTML) · อ่างเกิน 100% มีคำอธิบาย · ตัวเลขอ่างซ้ำเดิม ≥ 3 รายงานมีหมายเหตุ

## ใบ "สรุปค่าที่วัดได้ช่วงเหตุการณ์น้ำ-ฝน" (PR 3.3 · A4 แนวตั้ง)

ปุ่ม "พิมพ์สรุป A4" ในหน้ารายละเอียดของเหตุการณ์ (ปุ่มเดียว ไม่มีช่องกรอก — เจ้าของระบบสั่ง "ต้องไม่เพิ่มงานให้เจ้าหน้าที่") กดแล้วเปิดหน้าต่างพิมพ์ทันที · ข้อมูลทุกอย่างมาจากหน้ารายละเอียดที่โหลดอยู่แล้ว ไม่เรียกฟังก์ชันฐานข้อมูลเพิ่ม ไม่มี migration

| ส่วนในใบ | เนื้อหา |
|---|---|
| หัว | ชื่อ อปท. · ถ้าเหตุการณ์ยังเปิดอยู่มีแถบ "ยังไม่สิ้นสุด ณ เวลาที่พิมพ์ — ค่าที่วัดได้อาจเปลี่ยนหลังจากนี้" |
| 1. ช่วงเวลาและเหตุที่เปิด | ช่วงเวลา+ระยะเวลา · เหตุผลที่ระบบปิด · สัญญาณที่เปิดเหตุการณ์ (สถานีไหน ค่าเท่าไร) |
| 2. ค่ารายสถานี | ค่าสูงสุด/ใกล้ตลิ่งสุดพร้อมเวลา · ค่าล่าสุดที่จด · กราฟเส้นขาวดำ (เส้นขาดตรงช่วงที่สถานีไม่ส่งค่า) · สถานีที่ไม่มีค่ารวมเป็นบรรทัดเดียว "ไม่มีค่า ไม่ใช่ 0" |
| 3. ข้อความเตือน สสน. | ตามต้นฉบับทุกฉบับ ไม่ตัดแต่ง (เขียนเป็นตัวอักษร ไม่ตีความ HTML) |
| ท้ายใบ | เกณฑ์ที่ใช้เปิด (ชุดที่ N ตรวจย้อนได้) · ที่มาของค่า · คำกำกับ "ไม่ใช่การประเมินความเสียหาย การประกาศภัย หรือคำสั่งของหน่วยงาน" · ช่องลงนาม · บรรทัดที่มา "ข้อมูล ณ … ผ่านระบบ E-Service …" |

**ช่องลงนาม (ปากกาล้วน ไม่มีลายมือชื่ออิเล็กทรอนิกส์ ใช้ `govSignBlock.js`):** "ผู้จัดทำ" = บัญชีที่ล็อกอินพิมพ์ (ชื่อ+ตำแหน่งจากโปรไฟล์) · "ผู้รับทราบ" = ปลัดจากทะเบียนผู้ลงนามกลางเดิม (บทบาท clerk ระดับหน่วยงาน) · ยังไม่ได้ตั้ง = เส้นประ+ตำแหน่งสำรอง ไม่ใช่ช่องหาย · **ไม่ใช้คำว่า "รับรอง"** เพราะระบบไม่ควรทำให้ดูเหมือนมีผู้มีอำนาจรับรองความเสียหาย (ผู้รับทราบ = รับทราบว่ามีข้อมูลชุดนี้เท่านั้น) · ตำแหน่ง "รักษาราชการแทน" ตัดเป็น 2 บรรทัดตามกติกากลาง · ไม่บันทึก audit log เพราะใบไม่มีข้อมูลบุคคล

**ขนาด:** ฟอนต์/ระยะบรรทัด/@page ตาม `govDocStyle.js` (14pt ตามที่เจ้าของระบบกำหนด — ⚠️ ไม่ใช่ค่าตามคู่มือ ว ๒๐๑๙ ซึ่งระบุ ๑๖ พอยต์ ต้องเปิดตัวบทฉบับจริงก่อนอ้างว่าพิมพ์ตามระเบียบงานสารบรรณ) · **ข้อยกเว้นเดียว:** ตารางรายสถานี 12pt (น้ำเลามี 11 สถานี demo 12 — 14pt ทั้งตารางกินเกือบ 3 แผ่น) · หลายหน้าได้ ใช้ขอบ @page จริง (ไม่ใช่ padding ของ .sheet) หัวตารางซ้ำ แถว/ข้อความเตือน/ช่องลงนามไม่ขาดกลางหน้า · วัดจริงจาก PDF: เหตุการณ์เล็ก (3 สถานี 1 ข้อความ ไม่มีช่วงขาด) **1 แผ่น** · ทั่วไป (5 สถานี 2 ข้อความ) 2 แผ่น · น้ำเลา (11 สถานี) 2 แผ่น · เลวร้ายสุด (12 สถานีชื่อยาว ข้อความ 6 ฉบับยาว) 3 แผ่น

**นโยบายเก็บ (เจ้าของระบบอนุมัติ 2569-10-17): ยังไม่ลบอัตโนมัติ** — ขนาดข้างบนเป็นสมมติฐาน ยังไม่เคยวัดจริง (ตอนอนุมัติมี 0 เหตุการณ์ ตาราง 40 kB ฐานข้อมูล 49 MB จาก 500 MB) และไม่ทราบว่าระเบียบการเก็บรักษาเอกสารบังคับเก็บกี่ปี (**ต้องยืนยันกับฉบับปัจจุบัน** ก่อนเปิดลบอัตโนมัติ) · ทบทวนเมื่อเหตุการณ์สะสมเกิน 50 รายการหรือฐานข้อมูลเกิน 300 MB · ทางเลือกที่พิจารณาแล้ว: ลบเมื่อปิดเกิน 3 ปี / เก็บสรุปแล้วลบรายชั่วโมงหลัง 1 ปี (ต้องแก้ `water_event_tick` เดิม เสี่ยงกว่า)

## ช่องโหว่ที่รู้ (ยังไม่แก้ใน PR นี้)

- `thaiwater-watchdog` ยังไม่เฝ้างานนี้ ถ้า `water_event_tick` หยุดทำงานเงียบๆ จะไม่มีข้อความเตือนถึงเจ้าของระบบ (สถานะดูได้ที่ `job_heartbeats` แถว `water-event-tick` และหน้าเจ้าหน้าที่แสดงแถบ "ไม่ได้ตรวจมา X ชม." ให้เอง) · cron รอบจริงทำงานแล้ว 21 รอบต่อเนื่อง (ตรวจ 2569-10-17) — เพิ่มได้ในรอบถัดไป แต่ต้อง deploy Edge Function เอง และต้องรอให้ tick ลงสมุดสำเร็จอย่างน้อยหนึ่งรอบก่อน ไม่งั้นตัวเฝ้าระวังเห็นว่า "ยังไม่เคยทำงาน"
- เกณฑ์ซ้ำกัน 3 ที่ (SQL / `water-alert-notify` / `src/lib/waterSituation.js`) · `tests/water-events.test.mjs` อ่านเทียบกันให้ แต่ถ้าแก้เกณฑ์ต้องแก้ครบทุกที่
