# เหตุการณ์น้ำ-ฝนที่ระบบจดเอง (เฟส 3 · PR 3.1 ยังไม่มีหน้าจอ)

## ทำไมต้องมี

`water_readings` และ `water_warnings` ลบที่ 7 วัน พอเหตุการณ์ผ่านไปหนึ่งสัปดาห์ไม่เหลือบันทึกว่าน้ำขึ้นสูงสุดเท่าไร ขึ้นตอนไหน สสน. เตือนอะไร — ย้อนเก็บทีหลังไม่ได้ ต้องเริ่มเก็บก่อนเกิดเหตุ
PR นี้ทำเฉพาะ "ส่วนเก็บ" (ตาราง + ฟังก์ชัน + cron) ยังไม่มีหน้าจอ ไม่ส่งข้อความหาใคร ไม่มีอะไรออกสู่ประชาชน หน้าเจ้าหน้าที่กับสรุป A4 เป็น PR 3.2 / 3.3

## ระบบทำอะไร

`water_event_tick()` รันทุกชั่วโมงนาทีที่ 20 (sync นาทีที่ 10 → แจ้งเตือน Telegram นาทีที่ 15 → ตัวนี้) อ่านจากฐานข้อมูลเราเท่านั้น

**เปิดเหตุการณ์** เมื่อ "ค่าสด" ของ อปท. ที่เปิดโมดูลน้ำ-ฝน เข้าเกณฑ์ข้อใดข้อหนึ่ง — ชุดเดียวกับที่ส่งเข้ากลุ่ม Telegram ยกเว้นอ่าง:

| สัญญาณ | เกณฑ์ | ความสดของค่า |
|---|---|---|
| ฝน | 24 ชม. ≥ 90.1 มม. (ฝนหนักมาก ตามกรมอุตุฯ) | ไม่เกิน 3 ชม. |
| ระดับน้ำ | ต่ำกว่าตลิ่งไม่เกิน 1 ม. (ขั้นเฝ้าระวังขึ้นไป ตามกรมชลฯ) | ไม่เกิน 3 ชม. |
| สถานีเตือนภัย ews | ระดับ 2–3 (ตอนนี้ปิดใช้งานอยู่ทุกแถว) | ไม่เกิน 12 ชม. |
| ข้อความ สสน. | ระบุอำเภอ+จังหวัดเดียวกับ อปท. | ออกไม่เกิน 6 ชม. |

⚠️ **อ่างเก็บน้ำไม่ใช้เปิดเหตุการณ์** — อ่างอยู่ชั้น "น้ำมาก" (>80%) ได้เป็นเดือนในฤดูฝน เหตุการณ์จะไม่ปิด
ค่าว่างจากต้นทางไม่เข้าเกณฑ์และไม่ถูกแปลงเป็น 0 (ระดับน้ำว่างห้ามกลายเป็น "เสมอตลิ่ง")

**ระหว่างเหตุการณ์** คัดลอกค่าที่วัดได้ของทุกสถานีที่ใช้งานอยู่ของ อปท. (ฝน/ระดับน้ำ/อ่าง/ews) ลง `water_event_readings` ทุกรอบ พร้อมย้อนหลังก่อนเปิด 24 ชม. เพื่อเห็นช่วงน้ำกำลังขึ้น และคัดลอกข้อความ สสน. ของอำเภอ+จังหวัดนี้ลง `water_event_warnings` ตามต้นฉบับ

**ปิดเหตุการณ์** (ระบบปิดเอง ไม่มีคนกรอก):

| เหตุผล `close_reason` | เงื่อนไข |
|---|---|
| `calm` | ค่าสดไม่เข้าเกณฑ์ต่อเนื่อง 24 ชม. · รอบที่ไม่มีค่าสดพอตัดสิน (สถานีฝน/ระดับน้ำไม่ส่งค่าจริงภายใน 3 ชม.) **ไม่นับว่าสงบ** และเริ่มนับ 24 ชม. ใหม่ · เข้าเกณฑ์อีกครั้งก็เริ่มนับใหม่ |
| `data_lost` | ไม่มีค่าสดพอตัดสินเลย 48 ชม. (สถานีถูกปิด/ต้นทางล่ม) — ไม่ปล่อยค้างตลอดไป |
| `module_off` | อปท. ปิดโมดูลน้ำ-ฝน หรือถูกปิดใช้งาน |

ทุกเหตุการณ์จดเหตุผลที่ตรวจย้อนได้: `open_reason` = สถานีไหน ค่าเท่าไร วัดเมื่อไร (พร้อม `rule_version`) · `close_reason` + `ended_at` (เวลาที่เห็นสัญญาณ/ค่าสดล่าสุด) + `closed_at` (รอบที่ปิด)
อปท. หนึ่งมีเหตุการณ์เปิดค้างได้ทีละเรื่อง (unique index) · อปท. หนึ่งพังไม่ลากรอบของแห่งอื่นล้ม และลง `job_heartbeats` ชื่อ `water-event-tick`

## ตาราง (ปิดสนิท ยังไม่มี policy อ่าน)

- `water_events` — 1 แถวต่อเหตุการณ์
- `water_event_readings` — สำเนาค่าที่วัดได้ **พร้อมชื่อสถานี ไม่ผูก FK ไป `water_station_config`** เพื่อให้ลบ/เปลี่ยนสถานีทีหลังแล้วบันทึกเก่าไม่หาย
- `water_event_warnings` — ข้อความ สสน. ตามต้นฉบับ

ไม่เก็บชื่อ เบอร์ พิกัดของบุคคล (เทสต์ตรวจชื่อคอลัมน์) · RLS เปิด ถอนสิทธิ์ anon/authenticated ทั้งหมด · ฟังก์ชันเรียกจากเว็บไม่ได้

## ขนาดข้อมูล (สมมติฐาน ตรวจจริงเมื่อมีเหตุการณ์แรก)

สถานีรายงานราว 1 ค่า/ชม. · เหตุการณ์ 72 ชม. + ย้อนหลัง 24 ชม. × ราว 5–11 สถานี ≈ 500–1,100 แถว ≈ 100–200 KB ต่อเหตุการณ์ (ฐานข้อมูลฟรี 500 MB ใช้ไป ~44 MB เมื่อ 2026-10-01)
**ยังไม่มีการลบอัตโนมัติ** — ตัดสินนโยบายเก็บกี่ปีหลังเห็นขนาดจริง (ขอให้เจ้าของระบบเลือกตอน PR 3.2)

## ช่องโหว่ที่รู้ (ยังไม่แก้ใน PR นี้)

- `thaiwater-watchdog` ยังไม่เฝ้างานนี้ ถ้า `water_event_tick` หยุดทำงานเงียบๆ จะไม่มีข้อความเตือน (สถานะดูได้ที่ `job_heartbeats` แถว `water-event-tick`) — เพิ่มได้ในรอบถัดไป แต่ต้อง deploy Edge Function เอง และต้องรอให้ tick ลงสมุดสำเร็จอย่างน้อยหนึ่งรอบก่อน ไม่งั้นตัวเฝ้าระวังเห็นว่า "ยังไม่เคยทำงาน"
- เกณฑ์ซ้ำกัน 3 ที่ (SQL / `water-alert-notify` / `src/lib/waterSituation.js`) · `tests/water-events.test.mjs` อ่านเทียบกันให้ แต่ถ้าแก้เกณฑ์ต้องแก้ครบทุกที่
