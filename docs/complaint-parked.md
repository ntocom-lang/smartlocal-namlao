# สถานะ "ขึ้นทะเบียนรอดำเนินการ" (parked) ของคำร้อง

เจ้าของระบบสั่ง 2569-10-24: คำร้อง "ซ่อมแซมถนนทางการเกษตร" ของน้ำเลาถูกส่งมาแล้วแต่ อปท. ยังไม่พร้อมซ่อม
ลบก็เสียดาย (รูป/พิกัดคือข้อมูลความต้องการไว้ตอนวางแผน) ปิดเป็น "ดำเนินการแล้ว" ก็เป็นบันทึกเท็จ ใช้ "ปฏิเสธ" ก็ผิดความจริง

## กติกา
- เฟส 1 ของงานนี้ = สถานะใหม่ `parked` + ปุ่มพักเรื่อง/นำกลับเข้าคิว · เฟส 2 (ทะเบียนความต้องการบนแผนที่) กับเฟส 3 (ปิดเป็นกลุ่มเมื่อซ่อมเสร็จ) **ยังไม่ทำ**
- พักได้จาก `received` / `in_progress` เท่านั้น · หมวดต้องเปิดธง `complaint_categories.allow_parking` (ค่าตั้งต้นปิด ตั้งที่หน้า "ประเภทคำร้อง")
  — หมวดเร่งด่วน (น้ำท่วม ไฟฟ้า) ต้องปิดไว้ · หมวดเฉพาะกิจ (odor) ใช้ไม่ได้
- ใครพักได้: แอดมิน / superadmin / หัวหน้ากอง (officer) ที่เป็น "ผู้ทำงานของเรื่องนั้น" เท่านั้น — ผู้ลงมือ (staff/technician) ไม่มีสิทธิ์ ·
  สิทธิ์เดียวกันสำหรับนำกลับเข้าคิว
- ทางเข้า `parked` มีทางเดียวคือ RPC `park_complaints(uuid[], reason, note)` (ครั้งละ ≤ 200 เรื่อง · เรื่องที่ทำไม่ได้ถูกข้ามพร้อมรหัส ไม่ทำให้ทั้งชุดล้ม)
  — UPDATE/INSERT ตรงถูก trigger `guard_complaint_parked` ปฏิเสธทุก role ที่มาทาง API
- ทุกการพัก/นำกลับลง `complaint_timeline` (ใคร เมื่อไร เหตุผล) · ไม่ยิง Telegram ตอนพัก (ชุดหลายสิบเรื่องจะท่วมกลุ่ม) · ตอนนำกลับยิงตามปกติ
- นำกลับเข้าคิว = `received` + **กำหนดเสร็จนับใหม่** (`add_working_days` จากวันนี้ตาม `sla_days` ของหมวด) ไม่งั้นเรื่องที่พักมาหลายเดือนกลับมาเกินกำหนดทันที
- ผู้ร้องเห็น "ขึ้นทะเบียนรอดำเนินการ" + ข้อความมาตรฐาน (`PARKED_PUBLIC_NOTE`) ไม่เห็นเหตุผลภายใน ไม่เห็นวันกำหนดเสร็จ ไม่ขึ้นเกินกำหนด
- ไม่นับเป็นงานค้าง/เกินกำหนด/ผลงานผู้รับผิดชอบ · ไม่ปนใน "ดำเนินการแล้ว" และ "ปฏิเสธ" · สถิติสาธารณะ/สรุปรายเดือนแยกบรรทัดเอง
  (`complaint_stats*` ใส่คีย์ `parked` เฉพาะเมื่อ > 0 — ชุดสรุปรายเดือนที่ล็อกไว้เทียบ stats ทั้งก้อน ถ้าใส่ `parked: 0` ทุกเดือนจะถูกมองว่าต่างจากที่ล็อก)

## ข้อมูลติดต่อผู้ร้อง (PDPA) — การตัดสินของเจ้าของระบบ
- ประกาศเดิม: เก็บชื่อ/เบอร์ "5 ปีนับจากวันปิดเรื่อง" (`purge_expired_complaint_contacts`) — หมุดเวลาคือ `closed_at` ของเรื่องที่ปิดแล้วเท่านั้น
- เจ้าของระบบ 2569-10-24: **เรื่องที่อยู่ในสถานะรอดำเนินการไม่มีกำหนดลบ** พอซ่อมเสร็จและปิดเรื่องแล้วค่อยนับ 5 ปีตามเดิม
  → ไม่ต้องแก้ฟังก์ชันลบ เพราะ `parked` ไม่อยู่ในรายการสถานะของ `complaint_contact_retention_anchor` โดยเจตนา
  (เทสต์ `complaint-parked.test.mjs` ล็อกไว้ว่าห้ามเพิ่ม)
- ⚠️ ยังไม่ได้แก้ข้อความใน PDPA modal/ฟอร์ม (รอเจ้าของระบบ/DPO) ที่เสนอ: "เรื่องที่รอดำเนินการเก็บจนกว่าจะดำเนินการหรือยกเลิก"
  ประกาศเดิมยังไม่ผิดตามตัวอักษร (เรื่องยังไม่ปิด จึงยังไม่ถึงวันนับ) แต่เรื่องที่พักค้างหลายปีควรบอกผู้ร้องตรงๆ — ต้องยืนยันกับ พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคลฉบับปัจจุบัน
- ชื่อ/เบอร์ไม่ได้เป็นสิ่งที่ทะเบียนความต้องการต้องใช้ (รูป/พิกัด/รายละเอียดคือข้อมูลที่มีค่า และไม่ถูกลบด้วยกลไก 5 ปีอยู่แล้ว)

## ลำดับ rollout (ห้ามสลับ)
1. apply migration ทีละไฟล์ตามลำดับ (`20261025100000` → `100100` → `100200`) — NOTES ข้อ 3/10/11: บันทึก `schema_migrations` ให้ตรง prefix · ยังไม่มีเรื่องไหนเป็น `parked`
2. merge → CI deploy หน้าเว็บ (หน้าเว็บคิวรี `allow_parking` แยก พลาดก็ไม่พาชื่อหมวดหาย จึงไม่ผูกลำดับกับข้อ 1 แต่ควรทำข้อ 1 ก่อน)
3. ตรวจ prod: ป้ายสถานะ/แท็บ/หน้าติดตามเรื่อง ต้องรู้จัก `parked` ก่อนมีเรื่องจริงเป็นสถานะนี้ (NOTES ข้อ 1)
4. เปิดธง `allow_parking` ของหมวด "ซ่อมแซมถนนทางการเกษตร" (หน้า "ประเภทคำร้อง") → แอดมินเลือกเรื่อง → "ขึ้นทะเบียนรอดำเนินการ"

ย้อนกลับ: นำเรื่องทั้งหมดกลับเข้าคิวก่อน (`unpark_complaint` ทีละเรื่อง หรือ `UPDATE ... SET status='received'` ผ่าน SQL ภายใน — trigger ล้าง `parked_*` ให้)
แล้วค่อย `DROP` ฟังก์ชัน/trigger/คอลัมน์ได้ · CHECK สถานะต้องคงค่า `parked` ไว้จนไม่มีแถวเหลือ

## กับดักที่เจอระหว่างทำ
- `complaint_worker_can_act()` คืน **NULL** (ไม่ใช่ false) เมื่อเรื่องไม่มีผู้รับผิดชอบ (`assigned_to` เป็น NULL) และผู้เรียกไม่ใช่แอดมิน/หัวหน้ากอง
  → RPC เดิมที่เขียน `IF NOT FOUND OR NOT complaint_worker_can_act(...)` (`start_complaint_work`, `finish_complaint`, `edit_complaint_text`)
  ไม่ raise แล้วปล่อยผ่าน · `park_complaints`/`unpark_complaint` ห่อ `coalesce(..., false)` แล้ว · ตรวจ prod 2026-10-24: ยังไม่มีคำร้องที่ไม่มีผู้รับผิดชอบเลย (0 แถว) จึงเป็นช่องโหว่แฝง
  ที่ยังไม่ถูกใช้ — **ยังไม่ได้แก้ของเดิม** (เป็นฟังก์ชันที่ใช้ร่วม ต้องให้เจ้าของระบบตัดสิน: แก้ที่ตัวช่วยให้คืน `coalesce(..., false)` จุดเดียว)
- ฟังก์ชันตัวช่วยบน PGlite: เทสต์ฐานข้อมูลจำลองใช้ `complaint_worker_can_act` / `add_working_days` ที่ดึงจากไฟล์ migration จริง ไม่ใช่ของจำลอง

## เทสต์
- `npm run test:complaint-parked` — กติกาหน้าเว็บ + ผูกรหัส/ป้ายกับ migration + หน้าจอทุกจุดต้องรู้จักสถานะนี้ + ห้ามเพิ่ม `parked` ในหมุดนับ 5 ปี
- `npm run test:complaint-parked-db` — รัน migration จริงทั้ง 3 ไฟล์บน PGlite (ตั้ง `PATIENT_PGLITE_MODULE` ตาม docs/ai/PATIENT_BOOKING_HANDOFF.md)
  PGlite เป็น single connection: ไม่ใช่หลักฐานของ race ระหว่างสองคนกดพักชุดซ้อนกัน (ลดความเสี่ยงด้วยการเรียงรหัสก่อนล็อกแถว)
