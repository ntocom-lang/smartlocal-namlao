# แนวทางจาก Smart E-Office สำหรับ SmartLocal

สถานะ: เอกสารอ้างอิง ไม่ใช่ feature specification ที่อนุมัติให้พัฒนาทั้งชุด

แหล่งที่สำรวจ: [Smart E-Office Demo](https://smart.eoffice.buildbytoey.com/apps.php)

วันที่สำรวจ/ทดสอบ: 2026-10-26; จัดทำคลัง: 2026-10-28 (Asia/Bangkok)

## สรุปสำหรับอ่านก่อนเริ่มงาน

แนวคิดหลักที่สังเกตได้คือให้เรื่องหนึ่งเชื่อมหนังสือรับ–การเสนอ–หนังสือตอบ–งาน–ประชุม–เวียน–แฟ้ม ผ่านเลขอ้างอิงและประวัติเดียวกัน การนำมาใช้กับ SmartLocal ต้องต่อยอดบัญชี สิทธิ์ หน่วยงาน และโมดูลเดิม ไม่สร้างทะเบียนผู้ใช้หรือข้อมูลเรื่องซ้ำ

สำรวจ 70 เส้นทางจาก 9 Demo roles และวัด layout 70 หน้า × 9 viewport รวม 630 ครั้ง มีการทดลองธุรกรรมหลายกระบวนการจนจบ แต่ไม่ใช่การรับรองทุกปุ่ม ทุก role ทุกทางแยก ความถูกต้องของกฎหมาย หรือความปลอดภัยทั้งระบบ ข้อมูลนี้เป็น snapshot ตามวันทดสอบ ไม่ใช่ผลยืนยันสถานะปัจจุบันของเว็บภายนอก

นี่เป็นสรุปสำหรับ repo public จงใจไม่รวมข้อมูลรายการทดสอบ รายละเอียดบัญชี/ใบรับรอง ขั้นตอนทำซ้ำข้อค้นพบด้านความปลอดภัย หรือ URL ไฟล์เฉพาะรายการ ผลรายกรณีและหลักฐานอยู่ในรายงานฉบับเต็มที่เก็บแยกตาม [ดัชนีความรู้](README.md#ขอบเขตการเผยแพร่)

## ขอบเขตความเชื่อมั่น

- การเปิดหน้าที่สิทธิ์อนุญาตได้ HTTP 200 ไม่เท่ากับการยืนยันว่าเมนูนั้นทำงานครบ
- การบันทึกต้องดูผลหลังโหลดใหม่ และข้ามไปตรวจจากบทบาทที่เกี่ยวข้อง การคลิกปุ่มหรือเห็น toast อย่างเดียวไม่พอ
- ดูผ่าน UI และการเรียกที่ UI ใช้ ไม่มี source code, schema จริง, infrastructure หรือการพิสูจน์ key custody ของระบบภายนอก
- ภาพลายเซ็น/การกดอนุมัติ/QR ติดตามเอกสาร แยกจาก cryptographic digital signature การลงนามด้วยใบรับรองครบวงจรยังไม่ได้ยืนยัน
- ข้อความอ้างกฎหมายบน Demo เป็นเนื้อหาตัวอย่าง ต้องยืนยันกับฉบับปัจจุบันของงานสารบรรณ การมอบอำนาจ การลงนาม การเก็บ/ทำลาย และนโยบายข้อมูลส่วนบุคคลก่อนใช้งานราชการ

## บทเรียนที่ใช้กำหนดเกณฑ์ของ SmartLocal

ข้อกำหนดด้านล่างเป็นแนวทางออกแบบ/ตรวจรับ ไม่ใช่รายการเปิดเผยช่องโหว่ของเว็บภายนอก

- ใช้เรื่องอ้างอิงเดียว เชื่อมเอกสารและงานด้วย ID ภายใน ส่วนเลขหนังสือ/เลขรับเป็นข้อมูลทะเบียน อย่าคัดลอกชื่อเรื่องและผู้รับไปดูแลแยกทุกโมดูล
- สถานะเรื่อง สถานะขั้นพิจารณา และสถานะนำส่งเป็นคนละส่วน ต้องบอกผู้ถือเรื่อง เหตุผล และผู้ที่ดำเนินการได้ถัดไป
- ตรวจปุ่ม submit กับ form จริง ทดสอบด้วยการกดตามปกติและโหลดซ้ำ ไม่ใช้การเรียก handler หรือ force-click แทนการใช้งานจริง
- ตรวจ token ของแม่แบบอย่างเจาะจง อย่าเหมารวมข้อความในวงเล็บทั้งหมดว่าเป็นตัวแปรที่ยังไม่ถูกเติม
- OCR/AI เป็นข้อเสนอ ต้องแสดงค่าต้นฉบับ/ประโยคหลักฐานและให้แก้ได้ก่อนออกเลขหรือสร้างงาน ค่า confidence ไม่ใช่หลักฐานว่าค่าถูก
- การรักษาราชการแทนต้องแสดงทั้งผู้มีตำแหน่งและผู้ดำเนินการจริงอย่างไม่กำกวม พร้อมอ้างช่วงเวลาที่มีอำนาจ
- รูป/QR ไม่ใช่หลักฐานว่า PDF มี cryptographic signature ต้องแยกผลตรวจประเภทลายเซ็นและตรวจกรณีไฟล์ถูกแก้
- สิทธิ์อ่านไฟล์/ดาวน์โหลด/export ต้องตรวจฝั่ง server ด้วย ไม่อาศัยการซ่อนปุ่ม ใช้ negative tests ใน sandbox ที่ได้รับอนุญาต
- Audit ต้องแสดงผลตรวจล่าสุด ขอบเขตข้อมูลและสภาพตรวจไม่สำเร็จ ไม่ใช้ผลเก่ามาแสดงแทน ไม่สรุปสาเหตุโดยไม่มีหลักฐาน
- ทดสอบเลขซ้ำเมื่อ retry/ส่งพร้อมกันใน environment ที่เหมาะสม รักษาประวัติเลขยกเลิก ไม่ถือการลอง 2 หน้าต่างว่าเพียงพอ
- รอ animation/ข้อมูลตั้งต้นนิ่งก่อนเทียบตัวนับ ตรวจว่าดาวน์โหลดเป็น PDF จริง ไม่สรุปจาก HTML wrapper ของ browser viewer
- จำกัดการทดสอบให้เฉพาะข้อมูลที่สร้างเองใน Demo คง audit ของรายการที่จบกระบวนการ และยกเลิก/ปิด configuration ทดสอบที่ไม่ควรค้าง

## สิ่งที่ยังไม่ควรอ้างว่าผ่าน

| เรื่อง | สิ่งที่ต้องมีหรือทำเพิ่ม |
|---|---|
| Digital signature / batch signing | บัญชี sandbox ที่มีสิทธิ์ ใบรับรองพร้อมใช้ และกระบวนการจัดการกุญแจ; ตรวจ chain, หมดอายุ/เพิกถอน, แก้ไฟล์หลังลงนาม และลำดับออกเลข |
| Admin ทุกหน้า | สิทธิ์ sandbox ที่เจ้าของระบบจัดให้ ไม่ทดลองข้ามสิทธิ์ |
| ทำลาย/ส่งมอบเอกสารครบวงจร | เอกสารทดสอบที่เข้าเกณฑ์อายุและการอนุมัติตามระเบียบ ห้ามเอาข้อมูลของผู้อื่นมาทดลอง |
| ช่องทางภายนอก | ปลายทางทดสอบ LINE/email/e-Saraban ที่ได้รับอนุญาต พร้อมหลักฐานการรับจริง |
| แจ้งเตือนตามเวลา/cron | ตรวจ scheduler/log และกรณีไม่มี browser เปิด ไม่ใช้การกดปุ่มแทนข้อพิสูจน์งานเบื้องหลัง |
| Load / concurrency / backup restore | เกณฑ์โหลด, fixtures แยก, negative tests ข้ามหน่วยงาน/tenant และการกู้คืนใน sandbox |
| ตัวเลขสถิติ/accuracy | ตรวจต้นทางและวิธีคำนวณ ไม่ยกตัวเลขที่ระบบแสดงเป็น benchmark ที่พิสูจน์แล้ว |
| มือถือ/A4 ทุกแบบ | โทรศัพท์/เครื่องพิมพ์จริง กล้อง QR ปากกา native share, PWA และทุกแบบฟอร์มที่ต้องใช้ |

## ผลตรวจอุปกรณ์: เก็บเป็นข้อจำกัดของหลักฐาน

ตรวจ 320×568, 360×800, 390×844, 430×932, 768×1024, 844×390, 1024×768, 1366×900 และ 1920×1080px รวม 630 การวัด มีบางหน้าที่ต้องตรวจแก้ responsive ต่อ จึงห้ามสรุปว่า 70 เมนูใช้ได้ครบทุกอุปกรณ์

มีการทดสอบเพิ่มบน Chrome/Edge ของเครื่อง, Firefox และ WebKit และ touch emulation ตาม Pixel/iPhone/iPad descriptors บางกระบวนการ ผลระหว่าง engine ต่างกันได้ ต้องแยก layout viewport ออกจาก visual viewport และตรวจการแตะปุ่มจริง ปุ่มที่ยื่นพ้นจอไม่ถือว่าใช้งานได้แม้บังคับคลิกด้วย script สำเร็จ

WebKit บน Windows ไม่เท่ากับ Safari บน iPhone/iPad จริง และยังไม่มีผลตรวจโทรศัพท์จริงจากชุดนี้ เกณฑ์ SmartLocal ต้องยึดคำสั่งใน AGENTS.md เรื่องปุ่มอย่างน้อย 44px ชื่อเมนูครบ ไม่ล้นจอ และมาตรฐาน A4/govDocStyle/govSignBlock เดิม

### งานที่ระบบช่วยทำเองได้

| กลไก | ประโยชน์/งานที่ลด | ข้อเสียหรือกรณีผิด | ใครแก้ / หลักฐาน |
|---|---|---|---|
| ตั้งกฎตามประเภทเรื่องและกองครั้งเดียว | เติมผู้รับและกำหนด ลดเลือกซ้ำทุกเรื่อง | กฎหรือผู้ทำแทนล้าสมัยส่งผิดคน | ผู้ประสานงาน/ผู้ถือเรื่องเปลี่ยนพร้อมเหตุผล เก็บ before/after |
| เติมทะเบียน/เตือนซ้ำ | ลดพิมพ์ซ้ำและลงทะเบียนซ้ำ | รายการชื่อคล้ายอาจเตือนเกิน | เจ้าหน้าที่เทียบต้นฉบับและยืนยันข้อยกเว้น |
| เสนอกำหนด/งานจากข้อความ | ลดลืมกำหนดและกรอกงานใหม่ | ภาษากำกวม วันผิด หรือไม่มีหลักฐาน | เจ้าของเรื่องยืนยัน/แก้/ปฏิเสธ ไม่สร้างงานเองจากข้อความกำกวม |
| แจ้งเมื่อสถานะเปลี่ยน/ใกล้กำหนด | ลดโทรตามและเปิดหลายหน้า | แจ้งซ้ำ/ส่งไม่ถึง | ผู้ดูแลปรับกฎ ดูสถานะส่งและรวมสรุปเฉพาะข้อยกเว้น |
| ร่างรายงานประชุม/เลือกแฟ้ม | ลดคัดลอก/จัดแฟ้มซ้ำ | เติมเหตุการณ์ที่ยังไม่ยืนยันหรืออายุเก็บผิด | เลขานุการ/สารบรรณตรวจฉบับเดียว ผู้มีอำนาจยืนยันส่วนที่ต้องใช้ดุลพินิจ |

ระบบเตรียมข้อมูลและเสนอเส้นทางได้ แต่ไม่อนุมัติเงิน/พัสดุ ตัดสินสิทธิ ลงนาม หรือใช้ดุลพินิจแทนผู้มีอำนาจ ต้องยืนยันกับระเบียบปัจจุบันของแต่ละกระบวนการก่อนลงมือจริง

### ลำดับที่เสนอและต้นทุน

1. แกนเรื่องกับกล่องงาน: ใช้ portal/สิทธิ์/ทะเบียนเดิมก่อน ให้เจ้าหน้าที่เรียนรู้ flow เดียว
2. งานร่วมกัน: เพิ่มเวียน รายงานผล ประชุม และแฟ้มเฉพาะเมื่อหน่วยงานรับรองกระบวนการ
3. ตัวช่วย/การควบคุมสูง: OCR, digital signature, retention/destruction เมื่อข้อมูลและอำนาจพร้อม ไม่เริ่มด้วย visual workflow designer เต็มรูปแบบ

ค่า license/API/cloud เพิ่มต้องเป็น 0 บาท ใช้ของเดิมและโควตาฟรีที่ไม่ผูกบัตรก่อน ถ้าพื้นที่/egress/DB ไม่พอให้ลดขอบเขตหรือใช้ local processing ห้ามเปิดการคิดเงินอัตโนมัติ

ต้นทุนคนยังมี: สมมติฐานตั้งต้นของ pilot คือผู้ดูแลเทคนิคเดิม 2–4 ชั่วโมง/เดือน และผู้ประสานงาน 1–2 ชั่วโมง/เดือนสำหรับกฎและข้อยกเว้น ไม่ใช่ค่าที่วัดได้ และไม่รวมพัฒนา อบรม เหตุขัดข้อง หรือ restore ครั้งใหญ่ ยังประมาณวันพัฒนาไม่ได้จนกว่าจะเลือก scope และทำ gap analysis
